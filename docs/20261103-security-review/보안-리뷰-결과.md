## 1. 요약

**결론: 현재 상태로는 운영 배포를 하면 안 됩니다.**

가장 큰 문제는 **서버 API 전체에 인증이 없다는 점**입니다. 관리자 기능은 프론트엔드 주소를 `/joohee0229`로 숨겨 둔 것이 전부이고, 백엔드 `/api/admin/*`는 누구나 호출할 수 있습니다. 그래서 다음 일이 인증 없이 가능합니다.

- 고객 개인정보(이름, 전화번호, 카카오 ID) 열람
- 카카오 채널 이름으로 임의 고객에게 메시지 발송
- 챗봇·카카오 카드의 **"a-clic 바로 구매" 링크를 외부 사이트로 교체**
- 프로모션, 세미나, 홈 배너, 리드 데이터 생성·수정·삭제
- 파일 업로드

또한 `AGENTS.md`에 정한 **개인정보 AES-256 암호화 규칙이 실제 코드에 적용되어 있지 않습니다.** `encrypt()` 함수는 있지만 어디에서도 호출하지 않습니다.

## 3. 상세 발견 사항

### SEC-01 🔴 모든 API에 인증·인가가 없음 (관리자 API 포함)

**위치**
- `backend/src/routes/index.ts:16-25` — 라우터 등록부에 인증 미들웨어가 없음
- `backend/src/routes/admin.ts` 전체 — 대시보드, 제품 동기화, 프로모션·세미나·홈 배너 CRUD
- `backend/src/routes/leads.ts:6-37` — 리드 조회·수정
- `backend/src/routes/kakao.ts:16-29` — 친구톡 발송
- `backend/src/routes/consent.ts:6-51` — 수신 동의·거부
- `frontend/src/App.tsx:24` — 관리자 경로 `/joohee0229`가 공개 번들에 포함됨

**설명**

Express 앱은 `helmet`, `cors`, `morgan`, body parser만 쓰고, 인증 미들웨어는 없습니다. 관리자 화면은 추측하기 어려운 주소에 둔 것이 보호의 전부인데, 이 주소는 프론트엔드 JS 번들에 문자열로 들어 있어 누구나 볼 수 있습니다. 게다가 공격자는 프론트엔드 화면을 거칠 필요 없이 백엔드 `/api/admin/*`를 바로 호출하면 됩니다.

CORS 설정(`index.ts:19`)은 **브라우저**가 다른 출처의 응답을 읽지 못하게 할 뿐입니다. `curl` 같은 도구는 CORS를 무시하므로 접근 통제가 아닙니다.

**인증 없이 호출 가능한 위험 엔드포인트**

| 엔드포인트 | 할 수 있는 일 | 영향 |
|-----------|--------------|------|
| `GET /api/admin/dashboard` | 사용자·리드·세미나 수, 후속 상담 리드 20건과 **사용자 전체 레코드** 조회 (`include: { user: true }`) | 개인정보 유출 |
| `GET /api/leads` | 최근 리드 50건과 **사용자 전체 레코드** 조회 | 개인정보 유출 (이름, 전화번호, 카카오 ID, 후원자 번호) |
| `PATCH /api/leads/:id` | 리드 상태·메모·후속일 변경 | 영업 데이터 변조 |
| `POST /api/kakao/send` | 임의 `userId`(카카오 UUID)로 임의 메시지 발송 | 채널 명의 스팸·피싱, 발송 비용, 채널 제재 |
| `POST /api/admin/products/sync` | 임의 URL로 제품 생성·덮어쓰기 | SEC-02 참조 |
| `POST /api/admin/products/sync-all` | 전체 제품 재동기화 | 외부 호출 대량 발생, 서버 부하 |
| `POST/PUT/DELETE /api/admin/promotions` | 프로모션 생성·수정·삭제 | 고객에게 잘못된 프로모션 노출 |
| `POST/DELETE /api/admin/seminars` | 세미나 생성·삭제 | 일정 변조, 신청 내역 연쇄 삭제 (`onDelete: Cascade`) |
| `POST/PUT/DELETE /api/admin/home-promotions` | 홈 배너 생성·수정·삭제, 파일 업로드 | 홈 화면 변조, 파일 호스팅 (SEC-07) |
| `POST /api/consent/agree`, `/withdraw` | 타인의 수신 동의 기록 생성·변경 | 동의 이력 변조 (법적 증빙 훼손) |

**재현 예시 (로컬 개발 서버 기준)**

```bash

```

**권장 조치**

1. **관리자 인증 도입**
   - 관리자 계정은 사실상 1명(정주희 ABO)이므로, 최소한 서버 측 세션 또는 서명된 토큰 기반 인증을 도입합니다.
   - 비밀번호는 bcrypt/argon2로 해시하여 저장하고, 로그인 시도 횟수를 제한합니다.
   - 가능하면 2단계 인증(TOTP)을 추가합니다.
   - 토큰은 `HttpOnly`, `Secure`, `SameSite=Strict` 쿠키로 전달하는 방식을 권장합니다. 쿠키 방식을 쓸 경우 상태 변경 요청에 CSRF 방어를 함께 적용합니다.
2. **라우터 단위 적용**
   ```ts
   // backend/src/routes/index.ts (예시)
   router.use('/admin', requireAdmin, adminRoutes);
   router.use('/leads', requireAdmin, leadRoutes);
   router.use('/kakao/send', requireAdmin);   // 발송은 관리자 전용
   ```
   - `/api/kakao/webhook`은 관리자 인증 대상이 아니라 SEC-06의 출처 검증 대상입니다. 라우터를 분리하는 것이 안전합니다.
3. **프론트엔드**
   - `/joohee0229` 경로는 그대로 두어도 되지만, 보안 수단으로 간주하지 않습니다.
   - 관리자 화면 진입 시 로그인 화면을 거치게 하고, API가 401을 반환하면 로그인 화면으로 보냅니다.
4. **일반 사용자 식별** — SEC-04의 조치와 함께 설계합니다.

### SEC-02 🔴 인증 없이 제품 구매 링크를 임의 URL로 교체 가능

**위치**
- `backend/src/routes/admin.ts:49-62` — `POST /api/admin/products/sync`가 받은 `url`, `code`를 그대로 전달
- `backend/src/lib/amwayProduct.ts:196-198` — `options.code`로 기존 제품을 찾음
- `backend/src/lib/amwayProduct.ts:214, 233` — `aClicUrl: url`로 저장
- `backend/src/lib/vector.ts:17-18, 35` — `aClicUrl`이 고객에게 보이는 `purchaseUrl`이 됨
- `backend/src/lib/kakao.ts:34` — 카카오 카드의 "a-clic 바로 구매" 버튼 링크

**설명**

제품 동기화 API는 URL이 암웨이 도메인인지 확인하지 않습니다. 받은 URL을 r.jina.ai를 거쳐 가져와 파싱하고, 결과를 제품으로 저장하면서 **요청에 들어온 URL을 그대로 구매 링크(`aClicUrl`)로 저장**합니다.

`code`를 함께 보내면 기존 제품을 찾아 **덮어씁니다.** 제품 코드는 공개 API(`GET /api/products`, `GET /api/products/:id`)로 알 수 있습니다.

결과적으로 공격자가 다음 순서로 실제 고객 피해를 낼 수 있습니다.

1. 공개 API로 인기 제품의 `code`를 확인
2. 암웨이 상품 페이지를 흉내 낸 피싱 페이지를 준비 (`상품명`, `가격` 등 파서가 읽는 형식)
3. `POST /api/admin/products/sync`에 `{ url: "<피싱 URL>", code: "<제품 코드>" }` 전송
4. 이후 챗봇과 카카오 채널에서 해당 제품을 추천할 때 "a-clic 바로 구매" 버튼이 피싱 페이지로 연결됨

SEC-01과 묶여 있지만, 인증을 넣은 뒤에도 관리자 실수(잘못된 URL 붙여넣기)로 같은 결과가 생길 수 있어 별도 항목으로 둡니다.

**참고: 내부망 SSRF는 해당하지 않음**

서버가 URL을 직접 가져오지 않고 `https://r.jina.ai/<url>`로 요청하므로, 공격자가 서버 내부망(예: `http://169.254.169.254`)을 직접 조회하는 SSRF는 성립하지 않습니다. 다만 임의 URL 조회를 외부 서비스에 대신 시키는 프록시로 쓰일 수 있고, r.jina.ai 쪽 사용량 제한에 걸릴 수 있습니다.

**권장 조치**

1. URL 화이트리스트 검증
   ```ts
   function assertAmwayProductUrl(raw: string): URL {
     const u = new URL(raw);
     if (u.protocol !== 'https:') throw new Error('https URL만 허용합니다.');
     if (!['www.amway.co.kr', 'api.amway.co.kr'].includes(u.hostname)) {
       throw new Error('암웨이 상품 URL만 허용합니다.');
     }
     if (!/\/p\/[A-Za-z0-9]+/.test(u.pathname)) throw new Error('상품 페이지 URL이 아닙니다.');
     return u;
   }
   ```
2. 저장 직전에도 `aClicUrl`이 허용 도메인인지 한 번 더 확인합니다 (`vector.ts`의 `purchaseUrlOrFallback`에서도 검증하면 이중 방어가 됩니다).
3. `code`로 기존 제품을 덮어쓸 때 SKU가 일치하는지 확인합니다.
4. 관리자 인증(SEC-01)을 적용합니다.

### SEC-03 🟠 개인정보 평문 저장, 암호화 키가 없으면 평문으로 동작

**위치**
- `backend/src/lib/crypto.ts:11-33` — `encrypt()`/`decrypt()` 정의
- 호출처 없음 — `rg "encrypt\(|decrypt\("` 결과 정의부만 존재
- `backend/src/routes/seminars.ts:26-33` — 세미나 신청자 `name`, `phone`을 평문 저장
- `backend/prisma/schema.prisma:14, 105-106` — `User.phone`, `SeminarApplication.name/phone`
- `backend/prisma/schema.prisma:130` — `ChatLog.content` (건강 상담 내용이 저장될 경우 민감정보)

**설명**

`AGENTS.md` 개발 규칙은 "개인정보(체성분, 전화번호 등)는 AES-256 암호화 후 저장"이라고 정하고 있지만, 실제 코드는 암호화 함수를 한 번도 호출하지 않습니다.

`crypto.ts` 자체에도 문제가 있습니다.

1. **Fail-open:** `ENCRYPTION_KEY`가 없거나 길이가 64자가 아니면 경고만 남기고 **평문을 그대로 반환**합니다(`crypto.ts:12-15`). `decrypt()`도 키가 없으면 입력을 그대로 돌려줍니다. 운영에서 키 설정을 빠뜨려도 아무도 모르고 평문이 저장됩니다.
2. **무결성 검증 없음:** AES-256-CBC는 암호문 변조를 감지하지 못합니다. AES-256-GCM 같은 인증 암호화(AEAD)를 써야 합니다.
3. **조용한 실패:** 형식이 맞지 않는 값(`:` 없음)은 복호화하지 않고 그대로 반환합니다(`crypto.ts:27`). 평문과 암호문이 섞여도 구분할 수 없습니다.

**영향**

- DB 파일(SQLite) 또는 백업이 유출되면 전화번호·이름이 그대로 노출됩니다.
- SEC-01과 결합해 API로도 바로 노출됩니다.
- 개인정보 보호법상 안전성 확보 조치 관점에서 문제가 될 수 있습니다.

**권장 조치**

1. `crypto.ts`를 AES-256-GCM으로 교체하고 형식에 버전을 붙입니다.
   ```ts
   // 형식: v1:<iv hex>:<tag hex>:<ciphertext hex>
   const iv = crypto.randomBytes(12);
   const cipher = crypto.createCipheriv('aes-256-gcm', KEY, iv);
   const enc = Buffer.concat([cipher.update(plain, 'utf8'), cipher.final()]);
   const tag = cipher.getAuthTag();
   ```
2. 운영 환경(`NODE_ENV=production`)에서 키가 없으면 **서버 시작을 중단**합니다.
3. 전화번호·이름 저장 지점(`seminars.ts`, 사용자 생성·수정 지점)에서 암호화하고, 관리자 조회 시에만 복호화합니다.
4. 전화번호로 검색하거나 중복을 확인해야 한다면, 암호문과 별도로 HMAC-SHA256 해시 컬럼을 둡니다.
5. 기존 평문 데이터를 암호화하는 일회성 마이그레이션 스크립트를 준비합니다.
6. 체성분 수치나 채팅 내용을 DB에 저장하게 되면 같은 방식으로 암호화합니다.

### SEC-04 🟠 클라이언트가 보낸 `userId`를 신뢰함 (IDOR)

**위치**
- `backend/src/routes/reminders.ts:6-22` — `GET /api/reminders?userId=`
- `backend/src/routes/reminders.ts:24-46` — `POST /api/reminders`
- `backend/src/routes/consent.ts:6-51` — 동의·거부
- `backend/src/routes/chat.ts:7, 31` — `userId`를 그대로 AI 프롬프트에 넣음 (`ai.ts:75-76`)
- `backend/src/routes/seminars.ts:20, 28` — 신청 시 `userId`를 그대로 연결

**설명**

서버에는 "요청한 사람이 누구인지" 확인하는 수단이 없고, 모든 엔드포인트가 요청 본문이나 쿼리의 `userId`를 그대로 씁니다. 그래서 다른 사람의 `userId`를 알면(또는 추측하면) 그 사람으로 행동할 수 있습니다.

- 타인의 복용 리마인더(어떤 영양제를 언제 먹는지) 조회
- 타인 명의로 리마인더 생성 → 매일 그 사람 카카오로 메시지 발송 (`cron.ts:39-49`)
- 타인의 수신 동의·거부 기록 변조
- 세미나 신청을 타인 계정에 연결

`userId`는 cuid 형식이라 무작위 추측은 어렵지만, SEC-01로 `/api/leads`에서 사용자 ID 목록을 얻을 수 있으므로 실질적인 장벽이 되지 않습니다.

**권장 조치**

1. 사용자 식별 방식을 정합니다.
   - **카카오 채널 사용자:** 카카오 로그인(OAuth) 또는 카카오 챗봇 스킬 요청에 담긴 사용자 키를 서버가 검증한 뒤 서버 세션을 발급합니다.
   - **웹뷰 Mini-App:** 카카오 채널에서 웹뷰를 열 때 서버가 서명한 짧은 수명의 토큰을 URL에 붙여 넘기고, 웹뷰는 그 토큰으로 세션을 받습니다.
2. 서버는 세션에서 `userId`를 꺼내 쓰고, 요청 본문의 `userId`는 무시합니다.
3. 조회 쿼리는 항상 `where: { userId: session.userId, ... }` 형태로 범위를 제한합니다.
4. AI 프롬프트에 내부 사용자 ID를 넣을 필요가 없다면 제거합니다(`ai.ts:76, 273`).

### SEC-05 🟠 수신거부가 뉴스레터 발송에 반영되지 않음

**위치**
- `backend/src/routes/consent.ts:30-51` — 수신거부 시 `Consent` 테이블만 갱신
- `backend/src/lib/cron.ts:16-24` — 뉴스레터 발송 대상은 `User.isAgreed`로 조회
- `backend/prisma/schema.prisma:17, 27-38` — `User.isAgreed`와 `Consent`가 별도 필드

**설명**

수신 동의 상태가 두 곳에 나뉘어 있고 서로 동기화되지 않습니다.

- `/api/consent/agree`, `/api/consent/withdraw`는 `Consent` 테이블의 `isAgreed`만 바꿉니다.
- 매달 1일 뉴스레터 크론은 `User.isAgreed = true`인 사용자에게 발송합니다.
- 코드 어디에서도 `User.isAgreed`를 바꾸지 않습니다.

그 결과 **사용자가 수신거부를 해도 `User.isAgreed`가 `true`로 남아 있으면 광고성 뉴스레터가 계속 발송됩니다.** 반대로 동의해도 발송되지 않을 수 있습니다.

정보통신망법상 광고성 정보는 수신거부 의사를 밝힌 사람에게 보내면 안 되므로, 보안보다는 **법규 준수** 문제에 가깝지만 영향이 커서 High로 분류했습니다.

**권장 조치**

1. 동의 상태의 기준을 `Consent` 테이블 하나로 정합니다.
2. 크론 발송 대상을 `Consent`에서 조회합니다.
   ```ts
   const subscribers = await prisma.user.findMany({
     where: { consents: { some: { channel: 'KAKAO', isAgreed: true } } },
   });
   ```
3. `User.isAgreed`는 제거하거나, 동의 API에서 트랜잭션으로 함께 갱신합니다.
4. 광고성 메시지에 "(광고)" 표기와 수신거부 방법을 포함하는지도 함께 점검합니다.
5. 동의·거부 API에는 SEC-04의 본인 확인을 적용합니다. 지금은 누구나 타인의 동의 이력을 바꿀 수 있어 증빙으로 쓸 수 없습니다.

### SEC-06 🟠 OpenAI 비용 남용·서비스 거부

**위치**
- `backend/src/index.ts:22-23` — JSON·form 본문 10MB 허용
- `backend/src/routes/chat.ts:6-37` — 인증·호출 제한 없음
- `backend/src/lib/ai.ts:193-198` — `history`는 최근 10개로 자르지만 각 항목 길이 제한 없음
- `backend/src/lib/ai.ts:279-284` — 이미지(최대 약 7.5MB base64)를 GPT-4o Vision으로 전송
- `backend/src/routes/kakao.ts:6-14`, `backend/src/lib/kakao.ts:7-20` — 웹훅 출처 검증 없음

**설명**

`/api/chat` 한 번 호출로 OpenAI를 여러 번 부를 수 있습니다. 이미지 분석(GPT-4o Vision) 1회, 답변 생성 1회에 더해, Pinecone을 쓰는 경우 제품 검색마다 임베딩 생성 호출이 일어납니다(`vector.ts:270-276`). 체성분 키워드 검색과 응답 기반 연관 제품 검색(`ai.ts:110-124`)까지 합치면 요청 1회에 검색이 여러 번 실행됩니다. 인증도 호출 제한도 없으므로 누구나 스크립트로 반복 호출해 OpenAI 요금을 발생시킬 수 있습니다.

- 본문 10MB 제한 안에서 `history` 10개 항목에 긴 텍스트를 채우면 매 요청이 큰 입력 토큰을 씁니다.
- `/api/kakao/webhook`은 요청이 카카오에서 왔는지 확인하지 않아, 같은 방식으로 남용할 수 있습니다.
- OpenAI 계정에 사용 한도가 없다면 비용 피해가 커지고, 한도에 걸리면 정상 사용자가 서비스를 못 쓰게 됩니다.

**권장 조치**

1. `express-rate-limit` 등으로 IP·사용자 단위 호출 제한을 적용합니다. 예: 채팅 분당 10회, 이미지 분석 시간당 20회.
2. 본문 크기 제한을 경로별로 나눕니다.
   - 기본 `express.json({ limit: '100kb' })`
   - 이미지가 필요한 `/api/chat`만 별도로 큰 제한 (또는 이미지를 multipart로 받고 크기 제한)
3. `message`와 `history` 각 항목의 길이를 제한합니다(예: 2,000자).
4. 이미지 `mimeType`을 `image/png`, `image/jpeg`, `image/webp`로 제한합니다.
5. 카카오 웹훅 출처를 검증합니다. 카카오 i 오픈빌더 스킬 서버라면 스킬 URL에 비밀 경로나 헤더 값을 설정하고 서버에서 확인합니다.
6. OpenAI 대시보드에서 월 사용 한도와 알림을 설정합니다.

### SEC-07 🟡 업로드 파일 형식 검증이 약해 HTML·SVG 호스팅 가능

**위치**
- `backend/src/lib/upload.ts:12-16` — 저장 파일 확장자를 원본 파일명에서 가져옴
- `backend/src/lib/upload.ts:22-25` — 클라이언트가 보낸 `mimetype`만 확인
- `backend/src/index.ts:25` — `/uploads`를 `express.static`으로 제공

**설명**

multer의 `file.mimetype`은 클라이언트가 보낸 `Content-Type` 값이라 신뢰할 수 없습니다. 파일명을 `x.html`, `Content-Type`을 `image/png`로 보내면 검사를 통과하고 `promo-<랜덤>.html`로 저장됩니다. `express.static`은 확장자 기준으로 `text/html`을 응답하므로, API 서버 출처에서 임의 HTML 페이지가 제공됩니다. `.svg`도 마찬가지입니다.

`helmet()` 기본 CSP가 인라인 스크립트를 막아 스크립트 실행은 어렵지만, 정상 도메인에서 피싱 페이지나 악성 링크를 호스팅하는 데 쓸 수 있습니다. SEC-01 때문에 인증 없이 가능합니다.

**권장 조치**

1. 확장자를 MIME 화이트리스트에서 결정합니다 (원본 파일명 확장자를 쓰지 않음).
   ```ts
   const EXT: Record<string, string> = {
     'image/png': '.png', 'image/jpeg': '.jpg', 'image/webp': '.webp', 'image/gif': '.gif',
   };
   ```
2. 저장 후 파일 앞부분(매직 바이트)을 확인해 실제 이미지인지 검사합니다 (예: `file-type` 패키지). 아니면 삭제합니다.
3. `/uploads` 정적 제공 시 `X-Content-Type-Options: nosniff`(helmet 기본 포함)를 유지하고, 이미지가 아닌 확장자는 제공하지 않습니다.
4. 가능하면 업로드 파일을 오브젝트 스토리지(별도 도메인)로 옮깁니다.
5. multer 취약점(SEC-09)도 함께 업데이트합니다.

3. 리버스 프록시 뒤에 배포하며 `trust proxy`를 켜기 전에 proxy-addr을 반드시 업데이트합니다.
4. CI에 `npm audit --omit=dev --audit-level=high`를 추가하는 것을 검토합니다.

### SEC-10 ⚪ Host 헤더로 저장 이미지 URL 오염 가능

**위치:** `backend/src/routes/homePromotionAdmin.ts:9-13`

업로드한 이미지의 URL을 요청의 `Host` 헤더로 만들어 DB에 저장합니다. `Host` 헤더를 조작한 요청으로 배너를 만들면, 홈 화면 이미지가 공격자 서버 주소로 저장됩니다.

**권장 조치:** `PUBLIC_API_URL` 같은 환경 변수로 기준 주소를 정하거나, DB에는 `/uploads/<파일명>` 상대 경로만 저장합니다.

### SEC-15 ⚪ 운영 CORS 설정 기본값
